# d4 — 파일 기반 진행과 작업 순서

작성일: 2026-09-10. d1–d3 및 승인 기록은 보존하며, 충돌 범위에서 이번 합의가 우선한다.
후속 세부 구현 전체의 승인을 의미하지 않는다.

## 사용자 합의 근거

사용자는 작업별 기록, 완료 후 script 호출 방식, `.moondex/STATE.json` 같은 중단·재개 기록을 제안했다.
AI가 결과를 제출하고 advance를 호출하되 script가 검증·완료 판정·다음 작업 선택을 소유한다는 설명에 “응 맞아”라고 답했다.
“일단 스킬 관련된 부분은 무시하는게 좋겠어 … 바뀐 구조를 완성하고 그 다음에 기존 스킬들 개선”이라고 순서를 정했다.
가장 최근 요청은 “음 훅 제거가 우선이고 그 다음이 이전에 만든 새 구조를 진행하는거 같아”다.

## 채택 방향

1. AI는 결과·증거를 제출하고 script의 advance를 호출한다. AI가 공유 상태를 직접 done으로 바꾸지 않는다.
2. script가 승인 revision, 의존성, 필수 검증과 증거를 확인하고 done 전이 및 다음 ready 작업 실행을 담당한다.
3. 상시 watcher나 부모 세션 종료 후 무인 실행을 요구하지 않는다. 제출 후 advance 전 종료되어도 resume에서 미처리 결과를 발견한다.
4. 운영 상태는 프로젝트 로컬 파일로 저장한다. `.moondex/STATE.json`은 현재 상태와 재개 지점을 제공한다.
   plan.json, results/, events.jsonl은 파일 배치안이며 정확한 schema와 commit 순서는 구현 명세에서 정의한다.
   SQLite를 생산 runtime의 필수 의존성으로 두지 않는다. E1의 실험용 DB는 실험 증거로 보존한다.
5. 공유 상태는 script 단일 writer, 프로세스 간 lock과 atomic replace로 관리한다.
   여러 파일의 원자성까지 자동 보장된다고 가정하지 않는다. durable event와 snapshot 중 복구 권위,
   부분 기록 탐지·복구 순서 및 중복 외부 실행 방지는 구현 명세와 crash 시험으로 확정해야 한다.
6. 기존 스킬 일괄 정리·삭제·재작성은 새 구조 완성 후 별도 작업이다. 필수 진입 연결만 새 구조 범위에 포함한다.
7. 구형 baseline 전체 복구는 새 구조 착수 조건이 아니다. 재사용 코드의 관련 검증과 새 승인 의도를 검증하는
   필수 unit/integration/E2E는 유지한다. 과거 8개 실패를 통과로 바꾸어 기록하지 않는다.

## 계획과 수용 조건 영향

p2 I1→I2→I3→I4→I5→I6 의존 순서는 유지한다. I1/I2의 SQLite 가정은 파일 계약·lock·atomic write·replay로 대체한다.
I6의 기존 스킬 광범위 수정은 연기하고 새 진입점의 설치 실행을 우선 검증한다. 구형 SDD를 공존 제품 모드로 유지한다는 뜻은 아니다.
A01–A20 및 A21-r2의 사용자 의도는 유지하며 저장 매체에 종속된 시험 구현만 교체한다.
필수 추가 관찰: 결과 제출 직후 종료 후 resume, 동시 advance 충돌, snapshot 갱신 도중 종료,
중복 결과 전달, 검증 실패 결과의 done 거부, 무관한 완료 증거 재사용.

## 다음 구현 명세에서 구체화할 사항

- STATE/event/result 사이 commit·복구 순서와 schema version, revision/attempt 식별자.
- 한 번의 advance가 실행할 범위와 AI 판단이 필요한 반환 상태.
- unknown worker launch 및 살아 있는 test의 재연결·중복 방지 계약.
- 구체 실행 한도와 한도 소진 시 저장·개입·재개 조건. E1 한도를 제품 기본값으로 복사하지 않는다.

훅 정리 결과는 작업 로그에 별도 기록한다. 설정 파일 수정만으로 현재 세션의 runtime 반영이나 새 제품 동작을 보장하지 않는다.
