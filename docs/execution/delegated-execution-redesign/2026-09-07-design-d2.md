# d2 — E1 결과를 반영한 설계 보충

상태: d1의 사용자 승인 방향을 유지한 보충안. 새로운 지원 범위나 미제시 실행 명세의 승인을 추정하지 않는다.
원본 d1과 요구 r1은 불변이며, 변경된 판단과 이유만 이 revision에 기록한다.

## 유지하는 결정

새 execute 진입점과 legacy SDD 분리, immutable 기준/승인, SQLite 단일 writer,
기본 실행 agent 1개, 동일 기준/scope/한도 안의 자동 재계획,
실제 gate와 의도 검토, self-improve 별도 호출은 그대로 유지한다.

## E1에서 구체화한 계약

1. **Orca 실행 context**: 현재 live parent session의 Python subprocess가 Run/Task/worker-start/check/release/ack를
   수행할 수 있었다. 이 context를 최초 adapter 구현·검증 기준으로 삼는다.
   parent-ended/idle continuation은 별도 capability이며 미확인 상태로 표시한다.
2. **재수신 identity**: 동일 Delivery에서 `replayed`와 mutation request ID는 달라질 수 있다.
   dedup key는 message ID, batch 일치 검사는 runId+deliveryId+messages+count다.
   transport metadata를 immutable 업무 내용으로 취급하지 않는다.
3. **정리 순서**: durable inbox → 귀속 검사 → 별도 gate 실행 → effect 기록 → exact worker release → ack.
   gate 실패여도 settled worker의 정리 책임은 사라지지 않는다. 실행 완료는 gate PASS 여부로 구분한다.
4. **결과 신뢰**: Orca completed와 Moondex verified는 다르다. live worker 산출물에 별도 process oracle을 실행했다.
5. **budget**: 이번 E1의 600초/1 worker/0 retry는 실험 전용이다. 제품 실패 복구 2회 추천과 혼합하지 않는다.
   모델 ID/금액 telemetry가 없는 경우 unknown으로 표시한다.
6. **script 내구성**: intent-before-effect와 inbox commit은 유효한 출발점이다.
   하지만 실험의 staged scripts를 그대로 production core로 승격하지 않는다.
   독립 watchdog, lease/fencing, 외부 unknown outcome recovery, 전체 event transaction이 추가로 필요하다.

## 지원 표면 제안

초기 제품은 살아 있는 인증된 Orca context에서 실행/collector 재시작을 검증한다.
context가 사라지면 상태를 보존하고 정당한 재바인딩 가능성을 확인한다.
다른 terminal의 `--from` 지정이나 새 Run 생성으로 권한·한도를 우회하지 않는다.

"세션을 닫아도 계속된다"는 UX는 추가 실험 전 제공하지 않는다. 이 제한이 제품의 필수 기대와
충돌하면 실행 주체/Orca capability를 먼저 조정해야 하며 AI scheduling loop로 대체하지 않는다.
